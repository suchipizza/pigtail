## 1. Objectives

The pilot has three objectives, and no others:

1. **Check gate G1** (WORK_ORDER M4):
   - α ≥ 0.70 on every core field;
   - fewer than 10% of codebook categories changed in the last revision round;
   - 100% of claims have snapshots.
2. **Revise the codebook** from v0.1.0 and freeze the version that passes G1 as v1.0.0 (CB §13).
3. **Check that the process works end to end:** capture, unitizing, two coding passes through `LLMClient`, citation validation, adjudication, review queue, and the α computation. Measure cost and time per case.

**What the pilot does not do.** It makes no claim about any mechanism. With 3 winner/loser pairs it can't:
- support or contradict a mechanism;
- promote a card or change its `confidence`;
- estimate an effect.

Every statement about mechanisms, triggers, assets or outcomes in the pilot report goes in a section headed **"Exploratory (not pre-registered for inference; n = 3 pairs)"**. Nothing in that section is added to a card's `history`. Pilot cases don't count as supporting or contradicting cases for §9.3.

Outcome-threshold calibration (ADR-019, OM §9) is also a pilot task, but this document doesn't cover it. It needs its own pre-registration before any class base rate is computed (open issue 1). The only thing this document takes from the outcome model is the class labels used for case selection (§3), computed under `outcome-thresholds 0.1.0` as they stand.

## 2. Preconditions for starting attempt 1

Coding for attempt 1 starts only when **all** of these hold. The orchestrator records each check in RUNLOG.

1. This file, `docs/methodology/mechanisms/candidates.md`, and the pass A, pass B and adjudicator prompts (§5.2) are committed and pushed.
2. **Sources.** The evidence sources the core fields need are allowed to run under ADR-022 when coding starts. That means the GitHub REST/GraphQL API, and HN (Algolia + Firebase) once its CB controls exist. Why this is required: without HN (or another cleared community source), the units for C6, C7, C9 and C10 would come almost entirely from `release` and `none_observed`. The attempt would then fail G1 on thin or degenerate fields for reasons that have nothing to do with the codebook. That would use up one of the two attempts before the fourth step below. While a source is held, attempt 1 waits. This is an engineering dependency, not a human gate. Enabled sources and their coverage windows are listed in the selection addendum.
3. **Classes and privacy controls exist.** Outcome classes can be computed for the selection pool under `outcome-thresholds 0.1.0`, with cells of n ≥ 30 after fallback (OM §3.4). The pseudonymization and redaction controls required before model calls are in place (PRD §10, ADR-006).
4. The unit counts in §6.3 have been checked on the unitized data, and every core field meets its minimum. Unit counts are computed by code **before** coding. They reveal no codes and no agreement, so extending the sample to meet them (§4.4) doesn't count as looking at the data.

## 3. Case selection: 3 winners + 3 matched losers across ≥ 3 strata

WORK_ORDER M4 allows the pilot cases to be hand-picked. Here they are picked by a deterministic rule, and a human override is allowed only for the listed reasons (§3.5). No repo is named in this document or in any public output (ADR-022, CB-20, CB §12 P6). Cases are referred to by `case_id` only.

### 3.1 Selection pool (inclusion)
A case enters the pool if **all** of these hold at the selection date `S` (the day the selection script runs):
- It is in the case store with an anchor `T` (OM §2.2), and `S − 730 d ≤ T ≤ S − 93 d`. That is inside R4.1's trailing 24 months, and old enough that `T+90 + 3 d` settle lag has passed, so the T+90 class is final (OM §2.4).
- It is in the **calibration split**: `sha256("pigtail-outcome-holdout-v1" + case_id) mod 100 ≥ 30` (ADR-019). Held-out cases never enter the pilot.
- Its class under `outcome-thresholds 0.1.0` is final and not `unclassified`.
- Its primary category (the ADR-017 pipeline assignment made from inputs frozen at T, not a pilot code) is not `lists-learning` or `other`. Reason: lists have no adoption leg, and `other` has no definition to code against. Both are left for M6.

### 3.2 Exclusions
A case is excluded if any of these apply:
- **E1, personal-account repo.** The GitHub owner type was `User` at selection (ADR-022, CB-20, CB §12 P6; minimization while the interim holds apply). Only `Organization`-owned repos are eligible. This is a limitation (§10).
- **E2.** The repo is deleted, private or unreachable at `S`, or its stargazers-API series is truncated. The series counts as truncated when the connector detects it, or when the repo has more than 40,000 stars at `S` (the cap is unverified, OM §1.2).
- **E3.** A StarScout campaign flag is set (OM §4). If the filter hasn't run for the case's window, the flag is recorded as `unknown`, the case stays in, and the report says so.
- **E4.** It is one of the owner's registered launches, pigtail itself, or a case registered for a prospective prediction (R11.1). Those are controlled or prospective cases, not tuning material.
- **E5.** A snapshot the case needs can't be captured under ADR-010 or ADR-022. Concretely: no README at T can be retrieved, or no stargazers series exists.
- **E6.** The repo already appears in the pilot as another case. There is at most one case per repo, and the earliest T is kept.

### 3.3 Strata (≥ 3)
The three pairs sit in three distinct category strata. Each stratum is chosen to exercise a different module (CB §8):
- **S1 (AI):** `ai-apps-agents` or `ml-infra`.
- **S2 (devtools):** `devtools`.
- **S3 (other):** the remaining eligible category with the most eligible winners. Ties go to the category id that sorts first alphabetically.

A category stratum is a PRD R4.2 cell. The report also records, for each case, the other R4.2 strata: launch type (the derived `launch_mode` after coding), repo-age band, backing (`corporate_backed` module), and outcome class.

### 3.4 Winner and loser selection (deterministic)
1. **Winner order.** Within each stratum, eligible `winner` cases are sorted by `sha256("pigtail-pilot-v1" + case_id)`, ascending.
2. **Candidate losers.** For each winner in that order, the candidate losers are the eligible non-winner cases. The loser role can go to any class other than `winner`: `plateau`, `attention_only`, `short_lived` or `slow_riser` (OM §5.2). The candidate must:
   - have the **same primary category**;
   - have `|quarter(T_l) − quarter(T_w)| ≤ 1`;
   - pass the LSM caliper: `|LSM_l − LSM_w| ≤ 0.5 · SD_pool(LSM)`.
3. **Choosing among candidates.** Pick the one with the smallest distance
   `d = |ΔLSM|/SD_LSM + |Δlog10 age|/SD_age + |Δaudience band| / SD_band + |Δquarter| + 1[language differs]`,
   where each SD is the pool SD within the stratum. **Tie-break:** smaller `d` first, then the lower `sha256("pigtail-pilot-v1" + case_id)`.
4. **No partner.** If no candidate passes the calipers, move to the next winner in hash order. If no winner in the stratum has a partner, move the stratum to the next category under the S3 rule and log it.
5. Matching is **without replacement**.

### 3.5 Allowed overrides (the only "hand-picking")
After the automatic draw, the analyst may reject a selected case **only** for one of these reasons:
- (a) a manual check shows an exclusion from §3.2 that the automatic check missed;
- (b) the ADR-017 category is plainly wrong under the CB §9 boundary rules, **judged only on inputs frozen at T**;
- (c) capture fails for a required source after 3 attempts (WORK_ORDER §3).

Each rejection is logged in the private selection manifest with its reason code. The next case in the same order replaces it. The number of overrides and their reasons (not the repos) appear in the report.

### 3.6 Matching covariates (R4.3; all measured at or before T, except LSM)
| Covariate | Operational definition | Notes |
|---|---|---|
| Launch-signal magnitude `LSM` | `log10(1 + filtered stars in [T, T+48 h))`, from the stargazers API, `starscout_filtered` (OM §1.2) | Deliberately matches on early attention, so that the pair differs in follow-through. It overlaps with the first 48 h of `A30`; that is intended (R4.3 matches on launch signal). |
| Category | ADR-017 primary category at T | Exact match |
| Launch quarter | UTC quarter of T | Caliper ±1 quarter |
| Repo age at T | `log10(days from repo creation to T)` | — |
| Founder audience bucket | **Proxy:** reach band (CB §4.5, r1–r4) of the owner's prior audience, taken as the sum of stars with `starred_at < T` over the owner organisation's **other** public repos | Stays at organisation level, with no person-level lookup (E1 leaves only organisations). It uses only pre-T timestamps. This proxy is a design choice and needs an ADR (open issue 3). |
| Language | GitHub primary language at T | Distance penalty 1 if it differs |

### 3.7 Balance report (PRD §9.2; reported, **not gated**, at n = 3 pairs)
- **Continuous and ordinal covariates:** SMD = (mean_w − mean_l) / √((s²_w + s²_l)/2), with the pooled-SD form (LR [45]). Also report the variance ratio s²_w/s²_l.
- **Categorical covariates:** SMD per level on the indicator. For category it is 0 by construction.
- Report `|SMD| < 0.25` (the PRD gate) and `|SMD| < 0.1` (LR [47]) per covariate. When a pooled SD is 0, report "undefined (identical)".
- **No p-values** (LR [45][47]).
- **Why this doesn't gate:** with 3 pairs, the SMD is dominated by single cases and says little about how matching will behave at scale. The table is labelled "descriptive, n = 3; not an application of the §9.2 gate". An SMD ≥ 0.25 does **not** trigger re-selection, because re-selecting until balance looks good is a garden of forking paths. It is recorded as input for the M5 matching design (H-L10).

## 4. Reliability units and samples

### 4.1 Why the pilot needs a reliability supplement
Several core fields are measured per case or per burst: C4 and C5 (per case), C9 and C10 (per burst). Six pilot cases give at most 6 units for C4 and C5, and perhaps 6–12 bursts. That is below the minimum in §6.3, so those fields would be "not assessed", which fails G1 whatever the coders do.

The pilot therefore codes a **reliability supplement**: extra cases coded by exactly the same procedure. They serve only to measure α and the unknown rates. Coders are blind to outcomes (§5.4), so supplement cases don't need matching.

This adds units. It doesn't relax any gate: every field still needs α ≥ 0.70. It does need an ADR (open issue 2).

### 4.2 Samples
- **P (pilot):** the 6 cases from §3. Every field is coded on them.
- **SE (evidence supplement):** cases coded on **every** core field, with full evidence capture. The pool is the §3.1 pool after the §3.2 exclusions, any class (winner or not), with the pilot cases removed. Draw order: `sha256("pigtail-pilot-supp-v1" + case_id)`, ascending.
- **SC (case-level supplement):** cases coded on C4 and C5 only. Their inputs are frozen at T (repo description, topics, primary language, the first 4,000 characters of the README at T; OM §3.1). They need no external evidence, so they are cheap. The pool, exclusions and hash order are the same as SE, with SE and P cases removed.

### 4.3 Sizes
- **SE** is extended in hash order until C6, C7, C9 and C10 each reach the §6.3 minimum on (P ∪ SE), counted on the unitized data before any coding. **Cap: 40 cases.**
- **SC** is chosen so that `|P ∪ SE ∪ SC| = 60` cases for C4 and C5.
- **Stratified fill for SC.** SC takes up to 4 cases per eligible category in hash order. It then tops up so that the deterministic pre-signals for rare modules appear in at least 8 cases each:
  - `chinese_ecosystem`: README at T has a CJK character share > 50%, or a Chinese README variant file exists;
  - `relaunch_pivot`: repo age at T > 365 days.

  The pre-signals are computed by code from frozen inputs and are not coder output. Without them, the rare module fields would probably be degenerate (§6.4).

### 4.4 Rules
- Samples are drawn and unitized **before** coding. SE may only be extended because of unit counts, never because of codes or α.
- If SE reaches its cap and a field is still below its minimum, that field is `not assessed`, and G1 fails for this attempt (CB §10.1). This is recorded in the addendum before coding, so the result is known in advance and nobody can stop coding early.
- **Development set D.** Prompts are written and debugged on up to 5 cases from the pool that sort **last** in the SE hash order, after the §3.2 exclusions. D is disjoint from P, SE and SC. Codes on D are never used in any gating statistic.

### 4.5 Units per field (derived by code; CB §1 unitizing rule)
| Field | Unit | Coded on |
|---|---|---|
| C1 `reliability` | each coded item (every coded value on C2, C3, C6–C10 carries one) | P ∪ SE |
| C2 `first_party`, C3 `event_type_supported` | item inside a case-window snapshot [T − 90 d, T + 365 d] | P ∪ SE |
| C4 `category_primary`, C5 `module_active.<m>` (6 fields) | case | P ∪ SE ∪ SC |
| C6 `edge_type`, C7 `edge_evidence_level` | derived candidate pair | P ∪ SE |
| C8 `asset_category` | parser-extracted asset instance | P ∪ SE |
| C9 `trigger_type`, C10 `trigger_confidence` | burst (derived, CB §3.2) | P ∪ SE |
| C11a `presence`, C11b `direction` | case × candidate card (MC-01 to MC-13) | P ∪ SE (C11b only where the case has a final class, which is every case in P and SE) |

**Units excluded from α.** Some units get a value set by the pipeline before any coder sees them:
- `unknown` with reason `held`;
- `coverage_gap` taken from derived source-coverage metadata;
- `not_applicable` from an inactive module.

These aren't coder judgments, so they are excluded from α. Their count per field is reported. Without this rule, agreeing on forced `unknown` values would inflate α.

### 4.6 Selection addendum (committed before coding)
Before any coding, the orchestrator commits `docs/preregistration/YYYY-MM-DD-pilot-addendum-1.md` (README rule 4). It contains:
- the SHA-256 of the private selection manifest (the P, SE, SC and D case_ids and override log);
- the SHA-256 of the pinned codebook, thresholds and card files and of every prompt;
- the model ids and backend for each pass;
- the enabled sources and their coverage windows;
- the unit counts per field;
- the list of fields that are `not assessed` before coding, if any.

It contains no repo names.

## 5. Double-coding protocol (R7.2, R7.3, R7.4; CB §11)

### 5.1 Passes
| Pass | Prompt | Model | Sees |
|---|---|---|---|
| A | `pilot.code.A` (prompt family A) | `M_A` = `LLM_MODEL` (default `claude-opus-5`, ADR-007) | codebook 0.1.0 text + JSON, the unit, its evidence |
| B | `pilot.code.B` (prompt family B, written independently: different wording, different order of instructions, different examples) | `M_B`: a different model than `M_A` if the backend offers one at the start of attempt 1; otherwise `M_A` | same as A |
| Adjudicator | `pilot.adjudicate` | `M_A` | the evidence plus both codes, in an order randomized per unit (seed §8), with pass labels removed (LR [80]) |

- All calls go through `LLMClient` (PRD F15). The backend is whatever `LLM_BACKEND` is set to, and it is recorded.
- `M_B` is fixed in addendum 1 and not changed during the attempt.
- If `M_B = M_A`, the passes differ only in prompt. The report states that agreement may be inflated by shared model bias. If a second model later becomes available, an exploratory A-vs-C pass on the other model is allowed.
- Pass A and pass B run **independently**. Neither prompt contains the other pass's output. Pass B may run before, after or interleaved with pass A. No human or agent looks at pass B's codes before pass A is complete, and vice versa (analyst rule).
- **Cache.** The `LLMClient` cache key contains the prompt id and version (ADR-006). The two passes therefore never share cached outputs. Prompt-stability repeats bypass the cache.

### 5.2 Prompt versions
- Prompts are versioned `PromptSpec`s: `id`, `version`, and a `fingerprint` computed from the system prompt and template.
- They are frozen at version `1.0.0` for attempt 1 and committed before coding (§2 item 1).
- They may be changed only on development set D. Once gating coding starts, a prompt change voids the attempt (§7.3).
- Every coded value stores the provenance in CB §11.4:
  - `codebook_version = 0.1.0`
  - `prompt_id`, `prompt_version`, `prompt_fingerprint`
  - `model_id`, `llm_backend`
  - `coder_pass`, `run_id`, `coded_at`, `coder_confidence`

### 5.3 Prompt stability (exploratory, before freezing)
- On D, each prompt runs 3 times with the cache bypassed.
- The within-prompt agreement is reported. LR [78] has the method; the `promptstability` package is used if it installs cleanly, otherwise per-field α across the repeats.
- This check doesn't gate anything. It is reported as exploratory.

### 5.4 Blinding
- **What coders never see.** Prompts and the review UI don't show:
  - the outcome class;
  - the winner/loser role;
  - pair membership;
  - sample membership (P, SE or SC);
  - any outcome percentile.
- **Order and identifiers.** Case ids are replaced by random coding ids (seed §8). Cases from P, SE and SC are interleaved in a random order.
- **Inputs.** Inputs for C4 and C5 are frozen at T (OM §3.1), so they carry no outcome information.
- **Leakage that can't be avoided.** Coders who read case-window evidence can see bursts and mention volume, so part of the outcome can be inferred. This is recorded as a limitation. It isn't treated as a breach of blinding.
- **C11b.** `direction` needs the outcome. It is coded in a separate, later pass, after `presence` is locked (CB §11.6). In that pass both coders get the outcome class and dimension values. C11b is still double-coded, and its α is computed the same way.

### 5.5 Validation, adjudication and review
1. **Citation validation.** Every value from pass A and pass B goes through the citation validator (CB §11.1–11.2). A value that fails becomes `unknown` with reason `citation_failed` (snapshot or drop).
2. **What α is computed on.** α uses **the values after validation and before adjudication** (CB §11.5), because those are the values the pipeline would store. An α on the values before validation is reported as exploratory.
3. **Adjudication.** The adjudicator codes every unit where A and B disagree on a core field. It returns one value with a citation, or `unknown`. The citation is validated the same way.
4. **Review queue (R7.3).** These go to the queue:
   - every disagreement on a core field;
   - every value with `coder_confidence = low`;
   - an audit sample of 10% of agreed units per field, with at least 10 per field (seed §8).

   The `verifier` agent works the queue. A human works it too if H3 has been answered. The rate of wrong-but-agreed codes in the audit sample is reported per field as exploratory.
5. **Adjudicator and review outcomes don't enter α.** They produce the final coded dataset, and the codebook revision draws on them (§7.1).

### 5.6 H3: human calibration sample
The H3 status is checked in `ops/HUMAN_INPUTS.md` at the start of attempt 1.

**If H3 has been answered:**
- The human codes a random sample of gating units (seed §8) in the review UI. The human sees no LLM codes and no outcomes (§5.4), and finishes before seeing any other pass.
- Allocation order: 30 units each for C11a, C3, C9, C4 and C11b (the promotion-deciding fields, ADR-025), then the other core fields in C1–C10 order, until the human's time is used up.
- For each field with ≥ 30 human units, the LLM–human α between the human codes and the **adjudicated** LLM codes must be ≥ 0.70 (PRD §9.2). If it isn't, G1 fails.
- A field with fewer than 30 human units is reported as "not human-validated". That doesn't fail G1, because the PRD gate only applies where a human sample exists. The field carries the label below.

**If H3 hasn't been answered (the WORK_ORDER §5 default):**
- G1 uses LLM–LLM agreement only.
- **Every** pilot result, and every coded value produced under the resulting codebook, carries the label **"LLM-coded, not human-validated"**. That covers reports, D1/D2 displays and mechanism cards. It stays until a later human sample validates the field.

## 6. G1: how it is computed

### 6.1 Reliability data
For each α statistic, the reliability matrix has 2 coders (pass A and pass B) and one row per gating unit, excluding the units in §4.5.

**Gating units:**
- **Attempt 1:** P ∪ SE ∪ SC.
- **Attempt k ≥ 2:** a **fresh** block (§7.2). No unit whose disagreements were used to revise the codebook ever gates again.

### 6.2 Statistics and variants (CB §10.2–10.3; ADR-024 item 6)
| Field | α variant(s); each one gates |
|---|---|
| C1 `reliability` | ordinal α on {low < medium < high}, with unknown as missing; **plus** nominal α on known/unknown |
| C2 `first_party` | nominal α, with `unknown` as a value |
| C3 `event_type_supported` | nominal α |
| C4 `category_primary` | nominal α over the 15 ids |
| C5 `module_active.<m>` | nominal α, **one per module** (6 statistics) |
| C6 `edge_type` | nominal α (the 5 coded values, `none` included) |
| C7 `edge_evidence_level` | ordinal α on {none < inferred < attributed < explicit}, with unknown as missing; **plus** nominal α on known/unknown (CB §10.2 rule; see open issue 5) |
| C8 `asset_category` | nominal α over the 21 categories |
| C9 `trigger_type` | nominal α over the 13 types |
| C10 `trigger_confidence` | ordinal α on {low < medium < high}; **plus** nominal α on known/unknown |
| C11a `presence` | nominal α on {present, absent, unknown}, pooled over cards |
| C11b `direction` | nominal α on {supports, contradicts, neutral}, pooled over cards |

That makes **20 gating α statistics**:
- 12 fields;
- C5 split into 6 per-module statistics;
- a companion known/unknown statistic for each of C1, C7 and C10.

**Special values.**
- In nominal α, `unknown` and `not_applicable` are values. In the known/unknown companion, both map to `unknown`.
- In ordinal α, they are missing.
- A value dropped as `citation_failed` is `unknown`.

**Computation.**
- Krippendorff's α is computed from the coincidence matrix, as in LR [70]:
  - nominal δ² = 1[c ≠ k];
  - ordinal δ² from LR [70]'s ordinal metric on the ranks.
- The implementation must reproduce the worked examples in LR [70] before it is used. The verifier checks it against an independent open-source implementation, and the version is pinned in the report.

### 6.3 Minimum units per statistic
A statistic is **assessed** only if **all** of these hold:
1. **n_pairable ≥ 30.** n_pairable is the number of units with a value from both coders after missing values are removed. Ordinal α and the known/unknown companion count units separately.
2. **Expected disagreement D_e > 0.** At least two distinct values occur in the pooled values. When D_e = 0, α is undefined.
3. **For binary statistics** (the C5 modules and the known/unknown companions), the rarer value occurs **at least 5 times** in the pooled 2·n values.

**Why 30.** α = 1 − D_o/D_e. For a balanced binary field, D_e ≈ 0.5, so one disagreement among n units moves α by about 1/(n·D_e) ≈ 2/n.
- With n = 30, one disagreement moves α by about 0.07. The gate sits between two or three units.
- With n = 10, one disagreement moves α by about 0.2. Whether the field passes would then depend on a single unit.

Thirty also gives the unit-level bootstrap (§6.5) enough distinct resamples for a usable percentile interval. It is a design choice, not a published rule, and the report says so.

**Why the prevalence floor.** With a rare value, a single disagreement can push α to about 0 or below. The floor keeps the statistic from being decided by one or two units (the α version of the kappa "prevalence paradox").

**If a statistic is not assessed, G1 fails** (CB §10.1). The floor never makes a pass easier: a statistic below it doesn't pass.

**Companion statistics with no unknowns.** If **neither** coder used `unknown` or `not_applicable` on any unit, the known/unknown companion has no variation. The coders then agree perfectly on known-ness, so the companion is reported as "1.0 (degenerate: no unknowns)" and passes. If unknowns exist but fall below the prevalence floor, the α companion is replaced by a pre-registered **agreement bound** (ADR-029): the companion passes only if (a) the two coders' unknown rates differ by ≤ 0.05 **and** (b) raw agreement on known-vs-unknown is ≥ 0.95 over ≥ 30 pairable units. Otherwise it fails and G1 fails. This applies only to the companion statistics that ADR-024 added; the core-field α ≥ 0.70 of PRD §9.2 is unchanged.

### 6.4 Gate
The α part of G1 passes if and only if **every** one of the 20 statistics is assessed and has a **point estimate α ≥ 0.70** (PRD §9.2; ADR-025 keeps 0.70).

Also reported, but not gating:
- the 95% CI;
- the band from LR [71] (α ≥ 0.800 firm, 0.667–0.800 tentative; secondary source);
- whether each promotion-deciding field reaches α ≥ 0.80 with a CI lower bound ≥ 0.70 (the `high`-confidence condition, ADR-025).

A field that passes G1 but has a CI lower bound < 0.667 is flagged "tentative" in the report.

### 6.5 Bootstrap CI
- **Method:** a nonparametric bootstrap that resamples **units** (rows of the reliability matrix) with replacement. α is recomputed on each resample.
- **Resamples:** B = 10,000.
- **Interval:** percentile 95% CI.
- **Seed:** `numpy.random.default_rng(SeedSequence(20260925).spawn(20)[i])`, where `i` is the statistic's index in the §6.2 table order (C1 ordinal = 0, C1 companion = 1, …).
- **Degenerate resamples:** resamples where D_e = 0 are dropped and counted. If more than 5% are dropped, the CI is labelled "unstable".
- **Not KALPHA:** this is not the Hayes–Krippendorff KALPHA procedure (LR [68]). A KALPHA-style interval may be reported as exploratory.

### 6.6 Also reported per statistic (not gating)
- n units;
- n pairable;
- the unknown rate per coder, and the gap between coders (CB §10.2);
- the `citation_failed` rate per coder;
- raw percent agreement;
- the disagreement matrix, aggregated with no case ids.

### 6.7 "Fewer than 10% of codebook categories changed"
- **Denominator:** the 79 enum values listed under `g1_category_change_denominator` in `schemas/codebook/v0.1.0.json` (ADR-024 item 7):

  | Enum | Values |
  |---|---|
  | evidence types | 7 |
  | event types | 6 |
  | edge types | 4 |
  | edge evidence levels | 4 |
  | reliability levels | 3 |
  | asset categories | 21 |
  | trigger types | 13 |
  | modules | 6 |
  | categories | 15 |

  For a later round, the denominator is the count in the codebook version going **into** that round.
- **Numerator:** the changes in the revision round (version `V_k` → `V_k+1`), counted as follows:

  | Change | Counts as |
  |---|---|
  | value added | 1 |
  | value removed | 1 |
  | value redefined (a definition or decision-rule change in `codebook.md` that could change any code) | 1 |
  | pure rename (same definition) | 1 |
  | merge of two values into a new id | 3 (2 removed + 1 added) |
  | merge into one of the existing ids | 2 (1 removed + 1 redefined) |
  | split of one value into two new ids | 3 |

  - Every change is listed in the CHANGELOG with its type.
  - The verifier checks the count with a JSON diff of the enums plus a read of the `codebook.md` diff for redefinitions.
  - A wording-only change that can't change any code is a patch change and counts 0 (CB §13).
- **Pass:** numerator / denominator < 0.10. With 79 values, that means **at most 7 changes**.
- **"The last revision round"** is the revision made after the attempt that is being judged (§7.1).

### 6.8 "100% of claims have snapshots"
- **Scope.** Every stored coded value that isn't `unknown` or `not_applicable`, across passes A and B, the adjudicator, the human pass and the final dataset. Also every derived event (burst, quiet) and every quoted span.
- **What the verifier's validator checks.** It is run independently of the coding run, and for each claim it checks:
  - (a) each cited `evidence_id` exists in the evidence store;
  - (b) the snapshot object exists in private storage, and its SHA-256 equals the record's `content_hash`;
  - (c) the locator resolves: the text span is found after the permitted normalisation, the JSON pointer's value is equal, or the blob hash is present (CB §11.2).
- **Pass:** 100% of claims pass (a)–(c). A single failure fails G1, until the pipeline bug is fixed and the check re-run. That fix is a deviation, not a new attempt, because it doesn't change any code.
- **Also reported:** the share of values dropped as `citation_failed`, per field and pass.

### 6.9 Who decides
- The analyst computes G1 and writes `docs/reports/pilot.md`.
- The `verifier` recomputes every statistic from the stored pass data (CLAUDE.md: gate checks go to the verifier). Point estimates must match to 3 decimals, and CIs within 0.01 (Monte Carlo error).
- The **verifier's** verdict is the G1 verdict.

## 7. Revision, retry, failure and stopping rules

### 7.1 Codebook revision after each attempt
- After α is computed and **reported**, the analyst drafts the revision to `V_k+1`. The revision draws on:
  - the disagreement matrices;
  - adjudicator notes;
  - review-queue findings;
  - coder notes.
- Every change goes in the CHANGELOG with its type (§6.7) and reason. Unit ids go in the private log only.
- **What a revision may not do:**
  - it may not use outcome classes;
  - it may not demote a promotion-deciding field (C3, C4, C9, C11a, C11b) from core;
  - it may demote any other core field only with an ADR, and a demoted field can't feed any card or report claim (CB §10.3).
- Candidate cards may be revised at the same time. Card changes don't count toward §6.7, but they are listed.

### 7.2 Attempts
**Attempt 1:** code P ∪ SE ∪ SC with v0.1.0, then compute G1.
- **G1 passes** when every α statistic passes, the snapshot check passes, and the revision after attempt 1 changes at most 7 values (§6.7). Then:
  - **no changes:** v0.1.0 is re-labelled v1.0.0.
  - **1 to 7 changes:** the fields they affect are **re-coded** by both passes on a fresh confirmation block (drawn and sized as a fresh block under attempt 2 below) under the revised version. The attempt passes only if each affected statistic still reaches α ≥ 0.70 on that block. The revised version then freezes as v1.0.0.
- **G1 fails** when any of these three conditions fails. Then comes attempt 2.

**Attempt 2** (the one retry):
- The codebook is `V_2`, the revision made after attempt 1.
- The gating units are a **fresh block**: the next cases in the SE and SC hash orders, with no case from any earlier block, sized by the same §4.3 rules.
- The pilot cases P are re-coded under `V_2` for revision purposes, but they don't gate.
- Prompts may be updated to `2.0.0` on the development set D only, and are frozen before coding the fresh block.
- G1 is judged exactly as in attempt 1. The thresholds and the minimum-units rule don't change.

**Second failure:**
- Write `docs/reports/pilot-failure.md`. It covers:
  - the α per statistic for both attempts;
  - which fields failed and why (disagreement structure, unknown rates, unit counts);
  - what a re-scoped codebook would change.
- **No threshold is lowered** (WORK_ORDER M4; ADR-025).
- Re-scoping (for example: narrower definitions, fewer categories in an enum, splitting a high-inference field) is pre-registered as an **amendment** before attempt 3. The amendment states that pilot codes (not held-out outcomes) have been seen.
- If attempt 3 fails, M4-T3 is marked `blocked` with a diagnosis (WORK_ORDER §3 failure handling). The analysis layer stays gated on G1.

### 7.3 What counts as an attempt; stopping rules
- **No interim looks.** α is computed once per attempt, after passes A and B are complete on **every** gating unit of that attempt. Nobody computes α, percent agreement or disagreement counts on partial data. Monitoring completion counts, costs and error rates is allowed.
- **An attempt counts** (toward the limit of 2 before the failure report) once its α has been computed.
- **Voiding an attempt.** An attempt may be voided and restarted **only before** α is computed, and only for one of these reasons:
  - the model or backend becomes unavailable;
  - a pipeline bug corrupts inputs;
  - a prompt had to change.

  A voided attempt is logged as a deviation, and its partial codes are never used for gating.
- **Budget and usage limits.** When a usage limit is hit, the job pauses and resumes (R15.5). If the monthly budget ceiling (H1 default or owner-set) is reached, coding pauses until the budget resets. It doesn't stop the attempt, and it isn't a reason to shrink samples.
- **Fixed samples.** Samples are never shrunk after coding starts.

## 9. Report (`docs/reports/pilot.md`)
The report must contain:

Case-level content appears only by `case_id`. No repo is named (ADR-022, CB-20).

## 10. Known limitations (stated in advance)
1. **Only organisation-owned repos.** Because of E1, reliability on personal-account repos, which are probably a large share of OSS, isn't measured. The M5 pipeline-reproduction run must include them before M6 relies on the codebook for them.
2. **Partial blinding.** Case-window evidence shows attention (§5.4).
3. **Same-model passes may overstate agreement** when `M_B = M_A` (§5.1).
4. **Missing channels.** The unobservable channels (CB §6.4: Reddit, X, YouTube, Product Hunt and others) mean C9 codes describe observable triggers only.
5. **The supplement lets α describe the pool**, not the six pilot cases alone. That is intended: G1 is about the codebook, not the cases.
6. **Unverified proxies and caps.** The founder-audience proxy (§3.6) and the 40k-star cap (E2) are unverified design choices.
7. **Survivor-biased star series.** The stargazers-API series (ADR-012) is survivor-biased, which affects the classes used for selection.
8. **Outcome classes use provisional thresholds.** They are `outcome-thresholds 0.1.0`, before calibration.

## 11. Open issues raised by this pre-registration (for the orchestrator)
1. **Threshold calibration** (ADR-019, OM §9) needs its own pre-registration before any class base rate is computed. This file doesn't cover it.
2. **ADR needed:** the reliability supplement (§4). It makes the G1 fields assessable and relaxes nothing.
3. **ADR needed:** the founder-audience proxy (§3.6), i.e. the owner organisation's prior stars before T, banded.
4. **Resolved by ADR-029 before any coding (was: ADR needed before coding, if the rule is to change).** The strict companion rule (§6.3) can fail G1 because of one or two stray `unknown`s: the prevalence paradox. The options are to keep it (what this file does) or to replace the companion with a pre-registered bound on the unknown-rate gap between coders. Any change needs an amendment **before** attempt 1 starts.
5. **Codebook inconsistency.** CB §10.3 and the JSON list only "ordinal α" for C7, while CB §10.2 and ADR-024 item 6 require a known/unknown companion for **every** ordinal field. This file follows §10.2, since the codebook says the document wins for meaning. The JSON `core_fields[C7].alpha` needs a patch fix (`["ordinal", "nominal_known_unknown"]`).
6. **HN and other person-level sources are held** by ADR-022. Attempt 1 waits for them (§2 item 2), so the CB controls in ADR-022 are now on M4's critical path.
7. **Subscription backend.** ADR-023 says "no bulk person-level coding until LQ-1/2 are answered" in subscription mode. A pilot of about 50–100 cases with pseudonymized HN items should be confirmed as not "bulk", or routed to `api`, and the decision logged in an ADR.
8. **Where the pool comes from (ADR-028).** GH Archive can't detect breakouts, so the retrospective pool that §3.1 draws from depends on the screen M1-T18 chooses. Whichever screen it is, the pool's composition should be recorded in addendum 1, because it shapes which winners and losers can be drawn.
9. **LLM-label error correction** for downstream mechanism tests (CB §11.5, LR [79]) doesn't apply in the pilot, which runs no mechanism test. It is deferred to the M6 analysis pre-registration, which must name the estimator and the human-labelled subsample it needs.
